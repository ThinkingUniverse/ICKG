## 1. 第一处报错：torch infer_schema 不识别字符串注解

### 1.1 现状回顾
- 触发位置：`transformers/integrations/moe.py:250` 注册 `transformers::grouped_mm_fallback`，函数签名用 `from __future__ import annotations` 把 `torch.Tensor` 变成字符串注解。
- 旧 torch 的 `_library.infer_schema` 不解析字符串注解 → ValueError。
- 采纳方案：`pip install --upgrade torch torchvision torchaudio --index-url .../cu124` + 同步升级 `peft / accelerate / bitsandbytes`。

### 1.2 修复评估

| 维度 | 结论 |
|---|---|
| **根因定位** | ✅ 准确。`Got func with signature ('torch.Tensor', ...)` 带引号是关键证据，README 把这块讲透了 |
| **方案选择** | ✅ 升级路径比降 transformers 更前向兼容；A100 + 驱动 550.163.01 + CUDA 12.4 与 cu124 wheel 完全匹配 |
| **副作用** | ✅ 无。`torch 2.6.0+cu124 / transformers 5.8.1 / peft 0.19.1 / accelerate 1.13.0 / bitsandbytes 0.49.2` 这一套版本是当前主线 |
| **可重现性** | ✅ 升级是声明式的，conda env 重建会拿到同一组版本（前提是写到 `requirements.txt` / `environment.yml`） |

### 1.3 对正式训练 / vLLM 推理的影响
- **正式训练**：无负面影响。torch 2.6 在 A100 上 bf16 + flash-attn-2 路径稳定，烟测 20 步 GPU 利用率 99% / 64 GB 显存 / 没有 NCCL 抖动。
- **vLLM 推理**：无影响。vLLM 自带 CUDA / cuBLAS / cuDNN 版本固定，推理端跟训练端 torch 版本一致更省心。
- **唯一遗留点**：烟测日志里仍出现 `warmup_ratio is deprecated and will be removed in v5.2` 与 `logging_dir is deprecated`，当前已是 transformers 5.8.1 反而还在告警，意味着 5.8 系列还保留兼容但下个小版本仍可能拿掉。**建议在正式训练前**：
  - 把 `warmup_ratio` 替换为 `warmup_steps`（直接按 epoch / total_steps 反算）
  - 把 `logging_dir` 改为 `TENSORBOARD_LOGGING_DIR` 环境变量
  - 或者锁住 transformers 版本（在 requirements 里写 `transformers==5.8.1`）

### 1.4 验证建议
正式训练前再跑一次 `python -c "import torch, transformers, peft, accelerate, bitsandbytes; print(torch.__version__, transformers.__version__, peft.__version__, accelerate.__version__, bitsandbytes.__version__)"`，把版本号写进训练日志，便于复现。

## 3. 第三处报错：trl assistant_only_loss 模板检查（最值得说清楚）

### 3.1 修复方案速览
- 新建简化模板 [`baichuan_m2_training_template.jinja`](../../src/Fine_tuning/training/baichuan_m2_training_template.jinja)，删掉 tools / `last_query_index` 反向扫描 / `<think>` wrapping / tool_calls / reasoning_content 五段逻辑，加 `{% generation %}` 字面标记。
- [`train_qlora.py`](../../src/Fine_tuning/training/train_qlora.py)：训练前覆盖 `tokenizer.chat_template`，备份原模板；`trainer.save_model()` 后、`tokenizer.save_pretrained()` 前把原模板还原回 tokenizer，再写盘——这样 `adapter/` 目录里的 tokenizer_config.json 跟 base 模型字节一致，推理端读官方模板。
- 烟测 20 步成功，loss / accuracy 合理。

### 3.2 ✅ 修复结构上正确的部分

1. **绕过 trl 两道 gate 的思路是对的**：substring `"{% generation %}"` 必须字面出现 + prefix preservation。删掉 tools 分支让 `supports_tool_calling()=False`、删掉 `last_query_index` 让 `is_chat_template_prefix_preserving()=True`，三关全绿（验证见 [06_diagnostics_helpers_check.txt](trl_assistant_only_loss_chat_template/06_diagnostics_helpers_check.txt)）。✅
2. **`{% generation %}` 包裹范围正确**：`<|im_start|>assistant\n` 不进 loss（这是 prompt），`content + <|im_end|>\n` 进 loss（让模型学会自己 emit 停止符）。✅
3. **保存前还原官方模板的逻辑顺序正确**：`trainer.save_model(adapter_dir)` 只写权重，`tokenizer.chat_template = original_chat_template` 后再 `tokenizer.save_pretrained(adapter_dir)`，落盘的 tokenizer_config.json 就是官方模板。✅
4. **`assistant_only_loss=True` 触发的 token 掩码**：transformers 的 `AssistantTracker` 扩展会基于 `{% generation %}` 的字符 offset 反推 token mask，烟测里 `mean_token_accuracy=0.96` 说明 mask 落点合理，loss 没把 system / user 部分也算进去。✅

### 3.3 ⚠️ README 中的"字节完全一致"断言不成立（实测）

README 3.2 节原话："对当前训练数据，简化模板与官方模板渲染结果**字节完全一致**（验证过 3 条真实样本）"。

我用真实训练样本前 3 条跑了对照：

```
--- sample 0 bytes_equal: False
  diverge at char 8698
  official slice: 'im_start|>assistant\n<think>\n\n</think>\n\n[{"head":"Candida alb'
  simplifd slice: 'im_start|>assistant\n[{"head":"Candida albicans","head_type":'
--- sample 1 bytes_equal: False
--- sample 2 bytes_equal: False
```

**事实**：官方模板在「最后一轮 assistant」会无条件渲染 `<|im_start|>assistant\n<think>\n\n</think>\n\n[content]<|im_end|>\n`（因为 `loop.last=True` 且 `reasoning_content=''`，走的是官方模板第 51-52 行的 `<think>\n + reasoning_content.strip('\n') + \n</think>\n\n + content` 分支，空字符串 strip 后 reasoning 部分为空，但 `<think>\n\n</think>\n\n` 这个**空思考壳子**仍然存在）。简化模板把这层壳子去掉了。

也就是说，**实际两套模板的渲染并不字节相等，差了 `<think>\n\n</think>\n\n` 这 14 字节**。README 里那句话需要订正，不能误导后续 reviewer 以为"训练-推理两端用什么模板都无所谓"。

### 3.4 这个差异对训练 & 推理意味着什么？

关键问题：**模型在训练时学到的是「`<|im_start|>assistant\n` 之后直接 emit JSON」；那推理时它会被喂什么 prefix？**

在还原后的官方模板下，`apply_chat_template(messages, add_generation_prompt=True)` 的尾部行为受 `thinking_mode` 参数控制（实测）：

| 调用方式 | 推理 prompt 尾部 | 与训练分布是否匹配 |
|---|---|---|
| 默认（不传 `thinking_mode`）| `...<\|im_start\|>assistant\n` | ✅ 完全匹配训练 |
| `thinking_mode="on"` | `...<\|im_start\|>assistant\n<think>\n` | ❌ 模型没见过这个上下文 |
| `thinking_mode="off"` | `...<\|im_start\|>assistant\n<think>\n\n` | ❌ 模型没见过这个上下文 |

#### 推论

- **只要 vLLM / 推理代码不显式传 `thinking_mode`，训练分布与推理分布在 prompt 边界处完全一致**。这是当前最自然的调用方式。
- **如果有人显式传 `thinking_mode="off"` 想"关掉推理"**（看起来很合理的操作，因为我们的任务就是输出 JSON 不需要思考链），模型会被喂入它训练里从未见过的 `<|im_start|>assistant\n<think>\n\n` 前缀，从这里继续生成会得到不可预测的输出。
- **如果用官方模板原汁原味训练**，模型会学到「先 emit `<think>\n\n</think>\n\n`，再 emit JSON」。这种情况下任何 `thinking_mode` 都没问题，但每条样本都白白浪费 14 字符的 token、训练 effective length 也变短。简化模板的取舍是用"放弃 thinking_mode 兼容性"换"训练高效 + 输出干净"，对本项目（实体三元组抽取，不要思考链）是合理选择。

### 3.5 对正式训练的影响

- **训练本身**：烟测 50 样本 / 20 步 / loss 0.124 / token_acc 0.96 全部健康。简化模板下 `<|im_start|>assistant\n[JSON]<|im_end|>\n` 这段都被 mask 进 loss，模型学到的就是「prompt 之后直接产 JSON、并自己停止」——这正是我们要的。✅
- **训练 / 推理一致性**：上面 §3.4 表里"默认调用"那行是匹配的，所以**不会**因为简化模板带来训练-推理偏移。✅
- **遗留风险**：训练数据如果未来扩到包含 `<think>...</think>` 的真实思考链样本，**简化模板会丢掉中间的 think 段**（因为 simplified template 只 emit `message.content`），这会污染训练 label。当前 v1 数据集干净，OK；以后扩数据时要重新评估。

### 3.6 对 vLLM 推理的影响 ⭐ 重点

vLLM 调用 chat 接口时会用 `adapter/` 目录下的 tokenizer，其 chat_template 是**官方模板**（已还原）。所以模板渲染与 base 模型一致，特殊 token id 一致，no surprise。

**但请在部署时遵守以下两条硬规则**：

1. **vLLM 启动参数 / 客户端调用都不要传 `chat_template_kwargs={"thinking_mode": ...}`**（或对应的 OpenAI 兼容字段）。让 jinja 走默认分支，prompt 收尾就是 `<|im_start|>assistant\n`，与训练完全对齐。
2. **如果业务方要求"明确禁用 thinking"**，正确做法不是传 `thinking_mode="off"`，而是直接在 system prompt 里用自然语言说明，或者训练侧把数据改成带空 `<think>` 壳子的格式重训。当前简化模板路径下 `thinking_mode="off"` 会把模型送进训练分布之外。

#### 部署快速验证脚本

正式训练完成后、对外提供 vLLM 服务前，强烈建议跑一次：

```python
# 在服务器上，conda activate ickg
from transformers import AutoTokenizer
from peft import PeftModel, AutoPeftModelForCausalLM
import torch

ADAPTER = "/root/ICKG/models/Baichuan-M2-32B-QLoRA-v1/adapter"
tok = AutoTokenizer.from_pretrained(ADAPTER, trust_remote_code=True)

msgs = [
    {"role": "system", "content": "Extract triples from biomedical text."},
    {"role": "user", "content": "<your-test-sentence-here>"},
]

# 1) 确认 prompt 尾部就是 <|im_start|>assistant\n（不带 <think>）
p = tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True)
assert p.endswith("<|im_start|>assistant\n"), f"prompt ends with: {repr(p[-80:])}"
print("✅ inference prompt tail matches training distribution")

# 2) 加载 adapter，生成一段
model = AutoPeftModelForCausalLM.from_pretrained(ADAPTER, torch_dtype=torch.bfloat16, device_map="auto", trust_remote_code=True)
ids = tok(p, return_tensors="pt").to(model.device)
out = model.generate(**ids, max_new_tokens=256, do_sample=False)
print(tok.decode(out[0][ids["input_ids"].shape[1]:], skip_special_tokens=False))
```

如果第 1 步 assert 失败，说明 tokenizer 还原没成功（理论上不会，前面看了代码顺序是对的，但落盘后实际验证一下更稳妥）。
